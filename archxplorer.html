ArchXplorer — SoC 설계 탐색 플랫폼

아키텍처 검토를 스프레드시트에서 꺼내,
시뮬레이션으로 반복 탐색 가능한 제품으로 만들었다.

트랜잭션 레벨 시뮬레이터와 웹 서비스로 초기 단계 PPA 프로파일링과 FW 개발을 가능하게 한 사내벤처 제품. 센서 설계팀과 연구소에 배포되어 Milestone별로 IP 모델링과 샘플을 제공하며 실사용 중이고, 특히 TG interrupt timing에 따른 ISR 검증에 연구소가 적극 활용하고 있습니다.

내 역할 — 시뮬레이터 핵심 IP 모델 웹 서비스 UI/API DevOps 파이프라인

02

문제의식 & 해결방법론

이 플랫폼이 없던 시절, 초기 아키텍처 검토는 스프레드시트와 경험칙 계산이었습니다. 대역폭과 레이턴시를 엑셀로 추정하고 경험으로 마진을 잡는 방식인데, 근본 문제는 정확도 이전에 속도였습니다 — 검토 자체가 느려서, 아키텍처 안 하나를 바꿀 때마다 수작업 재계산이 따라붙고, 초기 단계가 요구하는 탐색 반복 횟수가 나오지 않았습니다.

그래서 접근을 뒤집었습니다. 검토를 "계산 문서"가 아니라 실행 가능한 시뮬레이션으로 만들면, 구성 변경은 재계산이 아니라 재실행이 됩니다. 탐색이 빨라질 뿐 아니라, 같은 환경에서 실리콘 이전에 FW까지 돌려볼 수 있게 됩니다.

방법론
Before — 문서 기반 검토

대역폭·레이턴시를 스프레드시트로 추정, 경험칙으로 마진 결정.

아키텍처 변경 1회 = 수작업 재계산 1회. 탐색 반복이 검토자의 손 속도에 묶임.

FW는 칩이나 FPGA가 나오기 전까지 실행 환경 자체가 없음.

After — 실행 기반 탐색

트랜잭션 레벨 시뮬레이터로 PPA 프로파일링. 구성 변경은 웹 UI에서 파라미터 수정 → 재실행.

코어 요청 상호작용(버스 경합)까지 모델링해 추정이 아닌 측정으로 판단.

같은 시뮬레이터 위에서 RISC-V 테스트 FW를 실리콘 전에 개발·검증.

정확도의 한계, 그리고 그 대신 잡은 것

트랜잭션 레벨 모델의 정확도에는 구조적 한계가 있습니다. 버스 레이턴시 모델링과 센서 IP 설계 분석으로 코어 요청 상호작용을 반영해 정확도를 15% 개선했지만 — 이 수치는 FW 전체 실행 cycle 시간 비교로 측정한 것으로, 측정 체계는 추후 고도화할 계획입니다 — 한계 자체를 없앨 수는 없습니다. 그래서 검증의 기준을 바꿨습니다. 사이클 수치의 절대 정합이 아니라 "FW의 ISR이 적절한 시점에 도는가"를 확인하는 것으로, 원하는 시점에 interrupt·bus IO·I2C를 주입하고 동작을 점검하는 mocking tool(host_communicator) 중심의 점검 체계를 세웠습니다.

방향도 그에 맞춰 진화하고 있습니다. 본래 목적인 최적화를 위한 다양한 확장 툴을 계속 개발하는 한편, 최근에는 "FW 선개발과 coverage 확보를 위한 사전 플랫폼"이라는 use case를 찾아 플랫폼의 의미를 넓혀가는 중입니다.

04

내가 겪은 일 — 트러블슈팅

EP.1 — "제품은 하나인데, 배포처의 세계는 셋이었다"
상황

센서 설계팀과 연구소에 배포를 시작하자 개발과는 전혀 다른 문제가 나타났습니다. 팀마다 실행 환경이 달랐고, 보안 요건상 서로 격리된 저장 환경을 유지해야 했습니다. 여기에 팀별 fork가 생기면서 IP 모델 관리가 갈라지기 시작했고, 정작 내부 개발자들끼리도 통일된 환경에서 final release를 통합 검증할 인프라가 없었습니다.

판단

환경을 하나씩 손으로 맞춰주는 건 팀이 늘 때마다 비용이 선형으로 늘어나는 길이라 버렸습니다. 대신 "환경 자체를 산출물로 만든다"로 방향을 잡았습니다 — 실행 환경은 Docker 이미지로 고정해 팀별 차이를 컨테이너 안으로 격리하고, 격리 저장 요건은 배포 채널을 분리해 수용하되 소스는 단일 트렁크로 관리해 fork 발산을 차단하는 구조입니다.

해결

GitHub Actions 기반 CI에 GTest(엔진·IP 모델)와 Cypress(웹 서비스 E2E)를 걸어, 모든 release가 동일한 통합 환경을 통과한 뒤에만 조직별 채널로 나가는 파이프라인을 구축했습니다. "누구 환경에서는 되는데"류의 이슈가 배포 단계에서 개발 단계로 당겨졌고, 다조직 체제의 운영이 사람이 아니라 파이프라인에 실리게 됐습니다.

EP.2 — 만든 사람이 첫 사용자가 되다: 이 프로젝트에서 얻은 역량
도구를 만들며, 도구로 일하며

플랫폼을 만들기만 한 게 아니라, ArchXplorer를 직접 사용하고 integration을 수행하면서 FW를 직접 개발하고 waveform으로 디버깅하는 역량을 얻었습니다. 만든 사람이 첫 사용자가 되니, 도구의 빈틈이 곧바로 다음 개선 항목이 되는 선순환이 생겼습니다.

깊어진 기술

특히 RISC-V CLIC(인터럽트 컨트롤러)와 코어 CSR을 통해 오류 지점을 진단하는 기술이 이 과정에서 깊어졌습니다. ISR이 적절한 시점에 도는지를 파형과 CSR 상태로 추적하는 이 진단 경험은 부팅 시간 25% 단축의 토대였고, 이후 파형 기반 프로파일링 툴체인에서 사용자 관점 요구를 정의할 수 있었던 밑천이기도 합니다.
