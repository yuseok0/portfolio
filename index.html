무엇을 하는 사람인가What I Do

SoC가 복잡해질수록 소프트웨어 개발은 실리콘이 나오기 전으로 당겨집니다. 그런데 그 구간에는 도구가 비어 있습니다. 소프트웨어 프로파일러는 "돌아가는 기계"를 전제하고, 하드웨어 검증 도구는 "신호를 보고 싶어 한다"고 전제합니다. 정작 "이 워크로드가 느린데 원인이 SW인가 HW인가, 그리고 어디인가"라는 질문에는 아무도 답하지 않습니다.

As SoCs grow more complex, software development keeps shifting to before silicon exists — and the tooling for that stage is empty. Software profilers assume a running machine; hardware verification tools assume you want to look at signals. Nobody answers the actual question: "this workload is slow — is it the software or the hardware, and where?"

제가 만들고, 함께 다듬어 온 것들은 전부 그 빈칸을 메우는 도구였습니다. 파형에서 소프트웨어 프로파일을 복원하고, 설정 파일의 값이 실제로 검증된 영역 안에 있는지 DV 코드로 대조하고, 펌웨어가 런타임에 계산할 값을 독립 모델로 미리 재현합니다. 공통 원리는 하나입니다 — 숙련자의 판단을 문서가 아니라 실행 가능한 파이프라인으로 옮기는 것.

Everything I have built or helped shape fills that gap: reconstructing software profiles from waveforms, checking whether a config value actually falls inside what DV code verified, and reproducing firmware's runtime calculations in an independent model. One principle runs through all of it — moving expert judgment out of documents and into executable pipelines.

지향 — 어디로 가는가Where I'm Headed

Vision

DV 세계에 Forward Deployed Engineer라는 영역을 개척하고 싶습니다. I want to pioneer the role of Forward Deployed Engineer for the DV world.

FDE는 고객의 현장에 들어가, 애매한 문제를 정의하고 해결의 형태로 만들어 전달하는 엔지니어입니다. 그 해결은 도구일 수도, 검증 서비스일 수도, 표준 산출물일 수도 있습니다. 검증의 세계야말로 이 역할이 비어 있습니다 — 설계팀, 솔루션, 고객사 사이에서 "무엇이 검증되었는가"라는 질문은 늘 번역 실패로 새고 있는데, 그 경계에 서는 사람이 없습니다.

A Forward Deployed Engineer walks into the customer's field, defines the ambiguous problem, and delivers it back in the shape of a solution — whether that is a tool, a verification service, or a standard deliverable. Verification is exactly where this role is missing — between design teams, solution teams, and customers, the question "what has actually been verified?" keeps leaking through failed translation, and nobody stands at that boundary.

저는 이미 그 일을 하고 있습니다. 고객의 애매한 요구를 constraint 계층 모델로 번역해 표준 deliverable로 만들었고, 검증 플랫폼을 제품으로 만들어 조직에 배포·운영했으며, 도구가 답해야 할 질문을 사용자의 자리에서 정의했습니다.

I am already doing this work: translating an ambiguous customer request into a layered constraint model and standard deliverables, shipping a verification platform as a product deployed across organizations, and defining — from the user's seat — the questions a tool must answer.

AI가 검증 코드를 대신 쓰는 시대일수록, 병목은 코드가 아니라 문제 정의와 현장 배포로 옮겨갑니다. 검증 요구를 스코프로, 스코프를 검증 서비스와 deliverable로 바꾸는 사람 — 그것이 DV의 FDE이고, 제가 만들려는 자리입니다.

As AI writes more of the verification code itself, the bottleneck moves from writing code to defining problems and deploying solutions in the field. Someone who turns verification needs into scope, and scope into verification services and deliverables — that is the FDE of DV, and that is the role I intend to build.

TLM 정확도의 구조적 한계를 인정하는 대신, 검증 기준을 "FW의 ISR이 적절한 시점에 도는가"로 잡았습니다. 원하는 시뮬레이션 타임에 interrupt·bus IO·I2C 데이터를 주입하고 결과를 확인하는 mocking tool(host_communicator) 중심의 점검 체계입니다. 최근에는 FW 선개발과 coverage 확보를 위한 사전 플랫폼이라는 use case로 플랫폼의 의미를 넓혀가는 중입니다.

Accepting the structural accuracy limits of TLM, we set the verification criterion as "does the firmware's ISR fire at the right time?" — a check system centered on a mocking tool (host_communicator) that injects interrupt / bus-IO / I2C data at chosen simulation times. The platform is now growing into a pre-development platform for early firmware work and coverage assurance.

문제 정의 — 내 기여의 시작점Problem definition — where my contribution starts

고객(AP 측)의 요청은 "API register 세팅 가이드를 달라"였지만, 실제 질문은 "검증 수준이 어디까지인가"였고 조직에는 그 답을 전달할 프로세스가 없었습니다. 나는 이를 FW / DV / Solution constraint의 3계층 모델로 분해하고, 레지스터 간 정합성 수식(Frame Length·Exposure Time 등)은 constraint가 아닌 별도 Guide 층위로 분리했습니다.

The customer (AP side) asked for "an API register setting guide" — but the real question was "how far does your verification actually go?", and the organization had no process to answer it. I decomposed this into a 3-tier constraint model (FW / DV / Solution), and split cross-register integrity conditions (frame length, exposure time) into a separate Guide layer rather than constraints.

Phase 1: machine-readable yet human-friendly YAML plus a browsable HTML view (shipped). Phase 2: a Python extension auto-validating bulk customer setfiles (in progress). Phase 3: a setting guide covering integrity formulas (feasibility under review). Alongside these, I am proposing process standardization — DV naming rules that make extraction unnecessary altogether.
