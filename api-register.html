Client용 API Register
검증영역 표준화 & Deliverable 생성

고객의 애매한 요구에서 진짜 질문을 꺼내,
암묵지였던 검증영역을 표준 산출물로 바꾸는 중이다.

이미지 센서의 API register를 고객(AP 측)이 안전하게 세팅하려면, "어디까지 검증되어 있는가"가 먼저 답해져야 합니다. 그 답이 조직 어디에도 문서로 존재하지 않던 상태에서, 문제 정의부터 산출물 체계까지 직접 설계하고 있는 프로젝트입니다.

내 역할 — 문제 정의 (컨설팅) Constraint 계층 모델 설계 Deliverable 포맷 설계·구현 주도
01

구성 — Constraint 계층 모델과 산출물 로드맵

이 프로젝트의 뼈대는 코드가 아니라 개념 모델입니다. "이 레지스터는 어디까지 안전한가"라는 질문에는 사실 서로 다른 세 개의 답이 있고, 기존에는 이 셋이 구분 없이 뒤섞여 있었습니다. 나는 이를 계층으로 분해했습니다.

FW Constraint

펌웨어가 선언하는 나이브한 값 범위. 가장 넓지만, "받아들인다"와 "보증한다"는 다릅니다.

출처 — FW 코드

DV Constraint

DV가 설계 문서를 근거로 짐작해 검증한 범위. 실제 시뮬레이션이 닿은 영역이지만, 그 경계가 코드 속 암묵지로만 존재했습니다.

출처 — DV(Verilog) 코드

Solution Constraint

솔루션 검증 단계가 실제로 확인한 범위. 대표 모드 조합 중심의 정적 검증이라, 레지스터 constraint의 극한까지 커버하지는 않습니다.

출처 — 솔루션 검증 기록

Guide (별도 층위)

단일 레지스터 범위를 넘어, Frame Length·Exposure Time 등 레지스터 간 정합성 수식을 만족해야 하는 조건. 고객이 최종적으로 원한 것은 이 층위였고 — 나는 이것을 constraint가 아니라 가이드로 분리해야 한다고 판단했습니다.

출처 — 타이밍 수식 · 도메인 지식

Deliverable 로드맵 — 고객 요구가 단계적으로 자란 순서 그대로
1차 — 구현

YAML + HTML

검증영역을 기계판독형 YAML로 — 단, 최대한 사람이 읽을 수 있게. 수동 열람용 HTML 뷰를 함께 제공.

2차 — 진행 중

Setfile 검증 Python 확장

고객이 bulky한 setfile을 보냈을 때, YAML 기준으로 값 유효성을 자동 판정하는 Python 확장.

3차 — 검토 중

정합성 Guide 레벨

Exposure Time·Frame Length 등 수식 조건까지 반영한 세팅 가이드. 검증 프로세스 자체가 없어 난이도가 높고, 가능성을 검토 중.

02

문제의식 & 해결방법론 — 요구를 받은 게 아니라, 요구를 찾아냈다

시작은 전형적인 고객 요청이었습니다 — "API register 세팅 가이드를 달라." 그런데 파고들수록 고객이 실제로 알고 싶었던 건 그 전 단계, "당신들의 검증 수준은 어디까지인가"였습니다. 그리고 그 질문에 조직은 답을 갖고 있지 않았습니다. 검증은 대표 모드 조합 중심의 정적 검증이었고, 레지스터 constraint를 극한까지 테스트한 적도, 그 결과를 전달하는 프로세스도 없었습니다. 프로세스가 없는데 고객이 무언가를 달라고 하니, 무엇을 줘야 하는지부터 아무도 몰랐던 것입니다.

Before — 무엇이 고장 나 있었나

검증영역은 DV 코드 속 암묵지였습니다 — 어디까지 검증됐는지는 코드를 읽은 사람의 머릿속에만. 문서는 수작업이라 릴리즈마다 누락과 불일치가 생겼고, 센서 프로젝트마다 전달물 포맷이 제각각이라 표준이라 부를 것 자체가 없었습니다.

방법론 — 세 번의 분리

① 질문을 분리했다. "세팅 가이드를 달라"를 "검증 수준을 알려달라 + 안전 범위를 알려달라 + 정합 조건을 알려달라"로 쪼갰습니다. 각각 답의 출처가 다르기 때문입니다. ② 출처를 분리했다. FW / DV / Solution constraint 계층 모델 — 같은 레지스터에 대한 세 답이 서로 다르다는 것 자체가 정보이고, 뭉개면 그 정보가 사라집니다. ③ 층위를 분리했다. 레지스터 간 정합성 수식은 constraint가 아니라 guide입니다. 범위 검사로 답할 수 있는 것과 없는 것을 섞으면, 산출물의 신뢰 경계가 무너집니다.

포맷은 기계판독과 가독성의 양립을 원칙으로 했습니다 — YAML은 파이프라인이 소비하고, 같은 데이터를 HTML로 렌더해 사람이 검토합니다. 문서와 데이터가 갈라지면 반드시 어긋나므로, 원천은 하나만 둡니다.

03

현황 & 기존 방식과의 비교

1차 산출물 구현 · 2차 진행 중 · 3차 타당성 검토
기준기존 — 수작업 문서이 체계 — 표준 산출물
검증영역의 소재 DV 코드 속 암묵지 — 코드 읽은 사람만 앎 YAML로 명시 — 출처(FW/DV/Solution)별 계층 표기
갱신 릴리즈마다 수작업 — 누락·불일치 상습 단일 원천에서 YAML·HTML 동시 생성
고객 setfile 검토 담당자가 케이스별 수동 확인 Python 확장으로 자동 판정 (2차, 진행 중)
프로젝트 간 이식성 프로젝트마다 포맷 제각각 스키마 표준화 — 새 프로젝트는 데이터만 교체
04

내가 겪은 일 — 트러블슈팅

EP.1 — "DV 코드에는 api_register가 없다"
문제

검증영역을 DV 코드에서 추출하는 일은 생각보다 훨씬 복잡했습니다. DV 코드는 Verilog라서 검증자가 레지스터를 아무 방식으로나 자유롭게 세팅할 수 있고, 통일된 룰이 없습니다. 결정적으로, DV 코드가 다루는 것은 HW 신호 층위라 api_register라는 개념 자체가 코드에 등장하지 않습니다. AI를 동원해 추출해도, 매핑을 판정할 명확한 룰이 없으니 결과를 신뢰할 수 없었습니다.

지금의 해법과 한계

지금은 케이스 바이 케이스로 검증 코드를 따져가며 수동 매핑하고 있습니다. 돌아가지만, 확장되지 않는 방식이라는 걸 압니다.

구조적 제안

그래서 추출을 더 잘하는 쪽이 아니라 추출이 필요 없어지는 쪽을 제안하고 있습니다 — DV 코드에 naming rule을 도입해 레지스터 세팅이 스스로를 설명하게 만들고, 규칙 위반을 sanity check로 걸러내는 가이드를 세우는 것. 시스템적으로 가야 다음 프로젝트에서도 살아남습니다. 일회성 문서가 아니라 프로세스를 남기는 것이 이 프로젝트의 진짜 목표입니다.

EP.2 — "FW와 DV의 말이 달랐다"
발견

같은 레지스터를 두고 FW constraint와 DV가 실제 검증한 범위가 어긋나는 경우들이 나왔습니다. FW는 받아들이는데 DV는 본 적 없는 값 — 고객이 그 틈의 값을 쓰면, 아무도 보증한 적 없는 동작이 필드로 나갑니다.

의미

이 불일치야말로 계층 모델이 필요한 이유의 실증이었습니다. 셋을 뭉개서 "스펙"이라는 한 단어로 전달해 왔기 때문에 아무도 이 틈을 볼 수 없었던 것이고, 출처별로 분리해 나란히 놓는 순간 틈이 표면으로 드러났습니다. 표준화의 가치는 문서가 예뻐지는 게 아니라, 불일치가 보이게 되는 것입니다.

EP.3 — 이해관계자 설득
과정

"고객이 달라는 것"과 "우리가 줄 수 있는 것"과 "책임질 수 있는 것"이 서로 다른 상황에서, FW·DV·솔루션 각 조직이 자기 constraint의 의미와 한계를 인정하는 합의를 만드는 일이 기술 작업만큼 컸습니다. 계층 모델은 이 협상의 언어이기도 했습니다 — 누구의 말이 틀렸다가 아니라, 각자 다른 질문에 답하고 있었다는 프레임이 합의를 가능하게 했습니다.
